# 版本与变更控制

基线版本：0.3.0

## 1. 原则

需求、设计、代码、数据、测试和文档构成一个不可拆分的发布基线。任何一项发生实质变化，都必须建立变更记录并更新全部受影响项；禁止只改界面或只改文档后直接发布。

## 2. 版本规则

采用 `主版本.次版本.修订版本`：不兼容架构/数据协议升级主版本；新增可兼容功能升级次版本；缺陷和文字修正升级修订版本。`VERSION` 与 `package.json` 必须一致。

## 3. 变更流程

1. 建立 `CR-YYYYMMDD-NNN`，描述原因、来源、优先级和验收口径；
2. 影响分析覆盖需求、数据、算法、设备、界面、数据库、性能、安全和论文指标；
3. 更新需求条目与追溯矩阵；
4. 更新设计、代码、配置、迁移和测试；
5. 更新用户/部署/验证文档与版本说明；
6. 运行同步校验和完整测试；
7. 评审批准后形成检查点并发布；
8. 记录发布结果和回滚点。

## 4. 自动门禁

`npm run verify:sync` 检查版本号、核心文档版本、事件节点、客流总量和设备数量。`npm test` 在此基础上执行生产构建和数据测试。未来CI必须把这两个命令设为合并与发布的强制门禁。

## 5. 追溯矩阵

`docs/traceability_matrix.csv` 为机器可读主表。每条需求至少关联一处设计、一处代码/配置和一项测试；未实现或受数据阻塞的条目必须标为 `deferred` 或 `blocked`，不得用“已完成”掩盖。

## 6. 数据与实验冻结

论文或专利使用的实验须冻结代码、配置、数据库快照、随机种子和原始结果。冻结后发现错误，应新建实验批次并保留旧批次，不覆盖原始数据。
